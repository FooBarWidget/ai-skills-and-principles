# Documentation quality assessment skill user guide

Must supply:

Audience: [example: fellow Kubernetes platform team members]
Purpose: [example: to discuss the state of an unimportant but poorly maintained service, and what the team should do about it]
Working context, if relevant: [Author–reader relationship, decision roles, stage of discussion, and relevant constraints or conventions.] [example: A platform engineer is briefing peers in a self-steering team. The report supports technical discussion; it is not for management or budget approval. The product owner, who is part of the team, handles planning and prioritization. Immediate repairs and longer-term architecture remain open for discussion. Changes elsewhere in the platform mean the team should reassess the existing design before committing to a replacement.]
[For collections where we want to assess navigation requirements, add this to working context: Site navigation must have at most two levels, both expanded by default. This constraint concerns site navigation, not heading depth within pages. The resulting navigation must also remain manageable in breadth.]
